# Step 7 - The lock-free command queue and the garbage queue

**English** | [繁體中文](step-07-commands.zh-TW.md)

[Overview](../README.md) | Previous: [Step 6](step-06-sends-buses.md) | Next: [Step 8 - PDC](step-08-pdc.md)

## Goal

Let the UI change the *structure* of a playing mix - add, remove, replace and reorder effects,
replace a track's clips - while the audio thread keeps running, without locks and without the audio
thread ever allocating or freeing memory.

## Design

### Why not a mutex?

A mutex makes the audio thread wait for whoever holds it. The UI thread holding it may be
preempted by the OS, may be resizing a vector (which allocates - and the allocator itself takes a
lock), or may just be slow. While it holds the lock, the audio thread misses its deadline: a dropout.
This is called **priority inversion**: a high-priority thread waits for a low-priority one. The
real-time rule is therefore "never wait", not "wait briefly".

### Values vs structure

| change | mechanism | why it is enough |
|---|---|---|
| fader, pan, mute, solo, send level, effect parameter, bypass, tempo, play | `std::atomic` | one number; the newest value wins; no memory involved |
| add / remove / replace / move insert, new clip list | **command** through `SpscQueue<Command>` | needs memory and several pointer updates applied together |
| an object the audio thread no longer uses | **garbage ticket** through `SpscQueue<Garbage>` | must be freed, but not on the audio thread |

### The single-producer / single-consumer ring buffer

Exactly one thread pushes (the UI) and exactly one pops (the audio thread). Then a ring buffer
with two indices needs no lock and no compare-and-swap loop - it is **wait-free**: every push and
pop finishes in a bounded number of steps.

```
slots:  [ 0 ][ 1 ][ 2 ][ 3 ][ 4 ]      capacity + 1 slots (one always stays empty)
              ^head           ^tail
        consumer reads slots[head]     producer writes slots[tail]
        empty: head == tail            full: (tail + 1) % size == head
```

Only the producer writes `tail_`, only the consumer writes `head_`. The memory ordering:

```cpp
// producer
slots_[tail] = item;                                   // 1. write the slot
tail_.store(next, std::memory_order_release);          // 2. publish it
// consumer
if (head == tail_.load(std::memory_order_acquire))     // 3. sees the publication...
    return false;
out = slots_[head];                                    // 4. ...so it sees the finished slot
head_.store(increment(head), std::memory_order_release); // 5. hand the slot back
```

The release store in (2) and the acquire load in (3) form a *happens-before* edge: everything the
producer wrote before (2) is visible to the consumer after (3). The same pair in the other
direction (5 / the producer's acquire load of `head_`) tells the producer that a slot may be
reused. The two indices are padded onto separate 64-byte cache lines so that the two CPU cores do
not keep invalidating each other's cache line (false sharing).

`T` must be trivially copyable - slots are overwritten by assignment and never destroyed - so a
`Command` carries raw pointers, never `unique_ptr`s or `std::vector`s.

### Ownership travels with the message

```
UI thread                                   audio thread
---------                                   ------------
fx = createEffect("Reverb")     (allocate)
fx->prepare(sr, block, 2)       (allocate, compute)
push(AddInsert{track 3, fx})  ----------->  pop -> chain.insertAt(slot, fx)          (pointers only)
push(RemoveInsert{track 3, 0}) ---------->  pop -> old = chain.removeAt(0)
                                            garbage.push(Garbage::of(old))
collectGarbage(): pop -> delete old  <----
```

`Garbage` is type-erased: a `void*` plus a plain function pointer that knows the real type,
generated by a capture-less lambda in `Garbage::of<T>()`. It stays trivially copyable.

Edge cases, all handled and tested:

- **Command queue full**: `pushCommand()` returns false, counts a drop, and deletes the payload at
  once (it never reached the audio thread, so the UI still owns it).
- **Chain full / invalid channel**: the audio thread cannot link the effect, so it sends it straight
  back as garbage.
- **Garbage queue full**: the audio thread may not free, so it *leaks* the object and counts it
  (`getGarbageLeaked()`). Every command produces at most one garbage ticket and both queues have the
  same capacity, so this cannot happen while `collectGarbage()` runs regularly.
- **Engine destroyed with commands pending**: the destructor frees their payloads.

### Observer pointers for the UI

`addInsert()` returns the effect's raw pointer. The UI keeps it to drive the editor and meters
(`setParameter`, `getMeterDb` are thread-safe). It stays valid until the effect is removed *and*
`collectGarbage()` has run - on the UI thread itself. So: only the thread that collects garbage
keeps such pointers. The insert slots are atomics, so `getInsert(channel, slot)` may be called from
the UI at any time.

## What you learned

- Never wait on the audio thread; a mutex can make you wait for the slowest thread in the system.
- Split changes into values (atomics) and structure (messages).
- A single-producer / single-consumer ring buffer needs only two atomic indices with
  release/acquire ordering.
- Allocation and deallocation happen on the UI thread; ownership travels inside the messages, and
  dead objects travel back the same way.
